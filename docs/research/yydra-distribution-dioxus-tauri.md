# Distribution ownership patterns: Dioxus, Tauri, and close analogues

_Research date: 2026-08-26. Scope: current official documentation and official project repositories only._

## Executive finding

Neither Dioxus nor Tauri uses one immutable manifest that simultaneously defines framework packages, CLI/template versions, copied project files, native projects, toolchains, tests/examples, and released application artifacts. Both use a layered model:

1. a project generator materializes a starting repository;
2. runtime/tooling stays versioned through Cargo and, for Tauri, an npm package manager;
3. project manifests and lockfiles become the runnable application's local authority;
4. platform projects and bundles are generated at later lifecycle stages; and
5. framework release metadata is separate from any application's release or updater metadata.

The closest official analogues reinforce the split. Backstage aligns a release across many npm package versions but excludes copied template state. Quarkus separates a compatibility BOM, a discovery catalog, and materialized codestarts. Rustup publishes a target-qualified, hash-bearing toolchain graph but knows nothing about product source or dependencies. `dist`/cargo-dist emits release-output inventory and checksums after product composition has already been decided.

For Yydra Q2, the smallest coherent V0 is therefore a Yydra-owned, immutable distribution manifest that **references** ecosystem-native authorities and records lifecycle semantics; it should not replace Cargo/npm locks, native project files, or release evidence.

## 1. Dioxus

| Question | Verified framework behavior | Yydra implication |
|---|---|---|
| Project creation and ownership | `dx new` writes a normal Rust project containing `Cargo.toml`, `Cargo.lock`, `Dioxus.toml`, assets, and `src/main.rs`; Dioxus also documents that `dx new` is optional and a project can be created manually. The official template repository says the CLI uses `cargo-generate` and its subtemplates to create projects. ([new-app tutorial](https://dioxuslabs.com/learn/0.7/tutorial/new_app/), [official template repository](https://github.com/DioxusLabs/dioxus-template)) | Treat template content as create-time materialization. After creation, the product repository—not the template repository—is the editable source of truth. Record the template/CLI version as provenance, not as continuing ownership. |
| Runtime dependency vs copied code | The generated `Cargo.toml` declares the `dioxus` crate and features; starter Rust, assets, and configuration are project files copied/generated by the scaffold. Fullstack target selection is driven by Cargo features in the application's manifest. ([new-app tutorial](https://dioxuslabs.com/learn/0.7/tutorial/new_app/), [fullstack project setup](https://dioxuslabs.com/learn/0.7/essentials/fullstack/project_setup/)) | Keep framework runtime as a versioned Cargo dependency. Do not model copied starter code as a dependency that can be upgraded in place. |
| Manifests and locks | Cargo owns Rust dependency declaration/resolution through `Cargo.toml` and `Cargo.lock`; `Dioxus.toml` owns Dioxus CLI configuration such as bundling/deployment settings. ([new-app tutorial](https://dioxuslabs.com/learn/0.7/tutorial/new_app/), [bundle guide](https://dioxuslabs.com/learn/0.7/tutorial/bundle/)) | A Yydra manifest should point at these files and their digests, not duplicate their complete semantics. |
| CLI/template/version coordination | Dioxus tells users to keep `dx` current and check `dx --version`; the 0.7 release notes say `dx` can self-update and warns when the CLI and `dioxus` crate are incompatible. The official examples on the repository's main branch target the Git version, while stable examples are kept on a release branch. ([tooling tutorial](https://dioxuslabs.com/learn/0.7/tutorial/tooling/), [Dioxus 0.7 release](https://dioxuslabs.com/blog/release-070/), [official repository](https://github.com/DioxusLabs/dioxus)) | Pin CLI and crate versions independently, then validate their supported pairing. Examples are release-line guidance, not a semantic component of an application distribution. |
| Mobile/native projects | Dioxus 0.7 uses `Dioxus.toml` to customize Android/iOS packaging. The CLI source builds an Android app directory under its build root and writes embedded Gradle, manifest, and wrapper assets into it; the iOS bundler consumes the already assembled `.app`. ([0.7 release](https://dioxuslabs.com/blog/release-070/), [Android builder source](https://github.com/DioxusLabs/dioxus/blob/main/packages/cli/src/build/android.rs), [iOS bundler source](https://github.com/DioxusLabs/dioxus/blob/main/packages/cli/src/bundler/ios.rs), [unified manifest source](https://github.com/DioxusLabs/dioxus/blob/main/packages/cli/src/config/manifest.rs)) | In the documented Dioxus flow, native packaging structure is regenerated build output. Prefer declarative `Dioxus.toml` ownership and do not make generated native directories a second authority unless Yydra explicitly adopts a supported escape hatch. |
| Upgrades and migrations | Dioxus publishes release-to-release migration guides, including 0.6 to 0.7, that require application manifest and source changes. ([migration index](https://dioxuslabs.com/learn/0.7/migration/), [0.7 migration guide](https://dioxuslabs.com/learn/0.7/migration/to_07/)) | A create-once/no-upgrade V0 may omit automated rebasing, but must say so. A future upgrade is a product-source migration, not template refresh. |
| Bundling/release output | `Dioxus.toml` configures bundle metadata; `dx bundle` emits platform applications/installers under `target/dx/...` and can report resulting paths as JSON. ([bundle guide](https://dioxuslabs.com/learn/0.7/tutorial/bundle/), [deploy guide](https://dioxuslabs.com/learn/0.7/tutorial/deploy/)) | Bundle inventory is build evidence. It does not replace the input composition contract. The reviewed official Dioxus sources do not document an application updater manifest analogous to Tauri's `latest.json`. |
| Canonical runnable source | This is an inference from the documented inputs: application source/assets plus `Cargo.toml`, `Cargo.lock`, and `Dioxus.toml`, interpreted by a compatible Rust toolchain and `dx`, are the durable project authority; `target/dx` is output. | A Yydra Distribution must capture the exact toolchain/CLI and hashes needed to interpret those authorities without claiming generated bundles are source. |

## 2. Tauri

| Question | Verified framework behavior | Yydra implication |
|---|---|---|
| Project creation and ownership | `create-tauri-app` asks for frontend language/framework/package manager and writes a runnable project. Its official contributor guide describes template directories and a `.manifest` whose file map is copied into the final template directory. ([create-tauri-app repository](https://github.com/tauri-apps/create-tauri-app), [template contributor guide](https://github.com/tauri-apps/create-tauri-app/blob/dev/CONTRIBUTING.md), [create-project guide](https://v2.tauri.app/start/create-project/)) | Like Dioxus, scaffold output is product-owned after creation. Preserve creator/template identity only as provenance. |
| Runtime dependency vs copied code | A Tauri app keeps `tauri` and `tauri-build` as Cargo dependencies; JavaScript frontends commonly keep `@tauri-apps/api`, plugins, the frontend framework, and the Tauri CLI as npm-family dependencies. The generated frontend, Rust commands, capabilities, icons, and configuration are ordinary project files. ([configuration files](https://v2.tauri.app/develop/configuration-files/), [project structure](https://v2.tauri.app/start/project-structure/)) | Model both dependency ecosystems and the copied source tree. Neither one lockfile nor Tauri configuration covers the whole application. |
| Manifests and locks | Tauri documents `tauri.conf.json` (or enabled JSON5/TOML form) as CLI/runtime application configuration, `Cargo.toml` as Rust dependency metadata, and `package.json` as frontend dependency/scripts metadata. It recommends committing `Cargo.lock` for consistent builds; the selected JS package manager supplies its own lockfile. ([configuration files](https://v2.tauri.app/develop/configuration-files/)) | The runnable authority is a set: Tauri config, Cargo manifest/lock, npm-family manifest/lock, source/assets, and any owned native changes. Yydra should identify the selected package manager rather than accept multiple ambiguous JS locks. |
| CLI/package/version coordination | Tauri says `tauri`, `tauri-build`, and the CLI should generally be kept on matching latest minor versions, though equality is not a strict requirement. Cargo and npm-family SemVer still perform resolution. ([configuration files](https://v2.tauri.app/develop/configuration-files/), [updating dependencies](https://v2.tauri.app/develop/updating-dependencies/)) | Pin the resolved CLI, Cargo, and npm package set and add an explicit compatibility validation; do not infer one version from a framework marketing release number. |
| Mobile/native projects | `tauri android init` creates an Android Studio project; Tauri documents the usual locations as `src-tauri/gen/android` and `src-tauri/gen/ios`. Crucially, official signing instructions tell application authors to create signing configuration in `gen/android` and edit `gen/android/app/build.gradle.kts`; mobile examples also direct edits inside the native tree. ([Google Play guide](https://v2.tauri.app/distribute/google-play/), [environment variables](https://v2.tauri.app/reference/environment-variables/), [Android signing](https://v2.tauri.app/distribute/sign/android/), [mobile multi-window example](https://v2.tauri.app/learn/mobile-multiwindow/)) | Tauri's `gen` name does **not** mean disposable-only: documented workflows require editable native state. The official pages reviewed do not impose one universal commit policy; Yydra must declare per path whether a native file is committed/product-owned, regenerated, or secret/machine-local. |
| Upgrades and migrations | Tauri provides migration guides and a CLI `migrate` command. For v1→v2 the command can translate the old allowlist to capability files, while the guide lists numerous package, import, plugin, configuration, and environment-variable changes that still require application work. ([migration overview](https://v2.tauri.app/start/migrate/), [v1→v2 guide](https://v2.tauri.app/start/migrate/from-tauri-1/)) | Upgrading is a multi-file source/dependency migration. A no-upgrade V0 should freeze the complete distribution and state that newly generated template/native output is not overlaid on an existing product. |
| Bundling and updater metadata | Tauri config drives application bundling. The updater plugin signs app update artifacts and accepts either a dynamic response or an application-owned static JSON whose required fields include `version`, per-platform `url`, and `signature`; Tauri Action can generate that JSON. ([distribution overview](https://v2.tauri.app/distribute/), [updater plugin](https://v2.tauri.app/plugin/updater/)) | `latest.json` is **application updater metadata**, not Tauri framework release metadata and not a build-input composition lock. It names deployable update artifacts but does not describe copied templates, full dependency resolution, tests, or toolchains. |
| Tests/examples/skills | Tauri publishes separate testing guidance and example repositories; these are development resources rather than entries in the application's updater schema. ([testing overview](https://v2.tauri.app/develop/tests/), [official examples](https://github.com/tauri-apps/tauri/tree/dev/examples)) | If Yydra distributes Skills, Evals, examples, or conformance tests, list them explicitly as typed distribution components. Do not assume a framework package/updater will carry them. |
| Canonical runnable source | This is an inference from Tauri's documented inputs and native edit workflow: the product repository's source, manifests/locks, Tauri configuration/capabilities, and retained native changes are authoritative; bundles and updater JSON are downstream outputs. | Validate that generation is clean from the declared authorities. If regeneration would erase an owned native edit, the ownership declaration is wrong. |

## 3. Framework release metadata is not application distribution metadata

| Layer | Dioxus | Tauri |
|---|---|---|
| Framework release | Published Rust crates, `dx` CLI releases, template repository/release line, migration notes. ([releases](https://github.com/DioxusLabs/dioxus/releases)) | Published Rust crates, npm packages, CLI/create-app releases, and migration notes. ([Tauri releases](https://github.com/tauri-apps/tauri/releases), [create-tauri-app releases](https://github.com/tauri-apps/create-tauri-app/releases)) |
| Application source authority | Product source plus Cargo/Dioxus manifests and lock. | Product source plus Tauri config, Cargo and JS manifests/locks, capabilities, and retained native source. |
| Application release metadata | `dx bundle` output/path reporting; no cross-input release manifest found in the reviewed official sources. | Bundle artifacts and optional updater responses/static `latest.json` with signed per-platform update locations. ([updater](https://v2.tauri.app/plugin/updater/)) |

The separation matters: a framework release can tell a creator which dependency/template generation to use; an application updater manifest tells installed copies which application artifact to download. Neither proves the entire source/toolchain/template composition that produced that artifact.

## 4. Closest open-source composition patterns

### 4.1 Backstage: coordinated dependency release plus one-time scaffold

The official Backstage versions repository publishes a release manifest consisting of an overall `releaseVersion` and `packages` with package names and versions. An installed app records its overall Backstage version in `backstage.json`; the Backstage Yarn plugin can resolve `"backstage:^"` dependency declarations against that version. `backstage-cli versions:bump` updates the coordinated Backstage dependencies. ([example 1.53.0 manifest](https://github.com/backstage/versions/blob/main/v1/releases/1.53.0/manifest.json), [keeping Backstage updated](https://backstage.io/docs/getting-started/keeping-backstage-updated/))

The same official update guide explicitly says Backstage is more library than application: `create-app` provides a starting point, and the generated `app`/`backend` packages do not automatically receive later template changes. Template changes are handled through the create-app changelog or Upgrade Helper. ([keeping Backstage updated](https://backstage.io/docs/getting-started/keeping-backstage-updated/))

**What it covers:** mapping one framework release to a compatible set of independently versioned npm packages. **What it does not cover:** template file inventory/digests, generated-versus-owned paths, toolchains, native projects, SBOM/provenance, or application artifacts. For Yydra, this is the best model for a compact logical release-to-package mapping, and a warning that copied scaffolds need a separate lifecycle contract.

### 4.2 Quarkus: BOM, catalog, and codestarts are separate authorities

A Quarkus Platform BOM constrains runtime/deployment extensions and third-party versions to a compatible set. A version-matched JSON platform descriptor is included through the BOM, identifies the platform, and is consumed by Quarkus tools to list/add/remove extensions. Quarkus documents the platform's promise as compatibility among any combination of extensions in that platform, under the platform producer's criteria. ([platform guide](https://quarkus.io/guides/platform/))

Codestarts are separately versioned artifacts containing templates and metadata. Creation tooling composes base and extension codestarts to materialize project skeleton, build tool files, language source, configuration, Dockerfiles/CI, and starter code. ([codestart guide](https://quarkus.io/version/main/guides/extension-codestart/), [extension metadata](https://quarkus.io/guides/extension-metadata))

`quarkus update` primarily applies OpenRewrite recipes to dependencies, source, and documentation, but Quarkus explicitly says it automates only a subset; users must inspect the diff, follow migration guides, build, and test. ([update guide](https://quarkus.io/guides/update-quarkus))

**What it covers:** dependency compatibility (BOM), discoverability/capabilities (descriptor/catalog), and create-time materialization (codestarts). **What it does not cover:** a byte-digest lock of the complete transitive build, continuous ownership of generated source, or guaranteed complete migration. Yydra should preserve these three roles even if one top-level manifest links them.

### 4.3 rustup: immutable, target-qualified toolchain distribution

Rust release channels key off a v2 TOML manifest with date, packages, components/extensions, renames, profiles, and per-target archive URLs and hashes. Published manifests have checksum and detached-signature sidecars; versioned and date-archived manifests coexist with mutable names such as stable/beta/nightly. ([Rust release channel layout](https://forge.rust-lang.org/infra/channel-layout.html), [rustup manifest parser](https://github.com/rust-lang/rustup/blob/main/src/dist/manifest.rs))

A product repository may commit `rust-toolchain.toml` selecting a channel/version/date plus profile, extra components, and targets. Rustup then installs managed binary components; it does not scaffold application source. The Rustup Book explicitly recommends tracking `Cargo.lock` separately when pinning a toolchain. ([toolchain overrides](https://rust-lang.github.io/rustup/overrides.html), [components](https://rust-lang.github.io/rustup/concepts/components.html))

**What it covers:** target applicability, component relationships/groups, downloadable artifacts, and integrity/authenticity metadata. **What it does not cover:** Cargo dependencies, product templates/source, non-Rust toolchains such as Android NDK, build recipes, or application migrations. Yydra should reuse the fixed-version/date, target, component-group, and hash ideas; a floating channel is not an immutable V0 pin.

### 4.4 `dist`/cargo-dist: released-output evidence, not composition authority

`dist` reads language manifests plus workspace/package dist configuration. Its config pins its own tool version for release-CI reproducibility, selects packages/targets/installers/artifacts, and can generate checksums, SBOM-related outputs, and extra artifacts. The machine-readable `dist-manifest.json` is produced by planning/building and describes the release/artifact result; the project ships a schema for it. ([configuration reference](https://axodotdev.github.io/cargo-dist/book/reference/config.html), [manifest schema crate](https://docs.rs/crate/cargo-dist-schema/latest), [official repository](https://github.com/axodotdev/cargo-dist))

**What it covers:** post-composition build plan/output inventory and delivery artifacts. **What it does not cover:** framework-package compatibility, creator template ownership, full product semantics, or consumer source migration. For Yydra it is an evidence producer that can be linked from a Distribution, not the Distribution's semantic authority.

## 5. Pattern synthesis for Yydra Q2

| Recurring role | Strongest pattern | Yydra V0 treatment |
|---|---|---|
| Logical release → ecosystem package versions | Backstage release manifest; Quarkus BOM | Record exact Cargo/npm coordinates and resolved lockfile digests. Keep native lockfiles authoritative for resolution. |
| Compatibility/discovery metadata | Quarkus platform descriptor | Record component identity, role, supported target, and compatibility constraints separately from file bytes. |
| Create-time copied/generated content | Dioxus/Tauri creators; Quarkus codestarts | Record generator/template identity, parameters, output path, and ownership mode: `copied-owned`, `generated-regenerable`, or `generated-customizable`. |
| Toolchain component graph | rustup channel manifest | Use fixed versions/dates, host/target qualifiers, download descriptors, and hashes. |
| Release artifact evidence | Tauri updater JSON; `dist-manifest.json` | Link artifact inventory, signatures, checksums, SBOM, and provenance as evidence. Do not treat it as the source composition contract. |
| Upgrades | Backstage coordinated bump; Quarkus/Tauri/Dioxus migrations | V0 may be create-once/no-upgrade, but must reject silent re-scaffolding and explicitly state that future upgrades are migrations. |

### Recommended smallest V0

Use one immutable, Yydra-owned JSON document as the **semantic composition index**, but keep its responsibilities narrow:

- identify the Yydra Distribution and schema version;
- list typed components: Cargo/npm dependency sets, CLI/generator/template, Skills/Evals/examples/tests, toolchains, and expected generated outputs;
- record each component's lifecycle/ownership (`dependency`, `copied-owned`, `generated-regenerable`, `generated-customizable`, `evidence`);
- qualify components by host/target and record immutable coordinates plus content digests where bytes are retrieved;
- link native authorities (`Cargo.lock`, one selected npm lockfile, configuration/native project files) by path and digest;
- link—not absorb—SBOM, provenance/attestation, signatures, updater metadata, and release-artifact inventories; and
- define a create-once V0 validation rule: generation succeeds from the pinned inputs, declared regenerated outputs match, retained product-owned files are never overwritten, and supported build/tests pass.

This gives Yydra a single answer to “what belongs to this Distribution?” without pretending that an inventory, catalog, lockfile, updater response, or attestation alone defines the product. None of the reviewed frameworks or analogues supplies that cross-ecosystem semantic contract; Yydra must own it.
