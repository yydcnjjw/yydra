# Yydra V0 mechanical quality tooling baseline

Date: 2026-08-31
Status: research input for **Define the mechanical quality and architecture contract**, not an implementation decision

## Scope and conclusion

This note maps the already-decided Rust/Axum/SQLx/PostgreSQL and React Native/Expo/TypeScript stack to concrete mechanical checks. It excludes taste-only rules: formatting remains useful because it makes generated and reviewed diffs canonical, but lint rules should enter the gate only when they catch a named correctness, portability, ownership, or maintainability failure.

The smallest credible V0 baseline is one public entrypoint, `yydra check`, which runs pinned project-local tools and Yydra-owned semantic checks without modifying the workspace. CI invokes that same entrypoint. Platform jobs may select `core`, `android-build`, or `ios-build` profiles, but those are profiles of the same contract rather than separately authored CI scripts.

Two checks need small Yydra-owned implementations because ecosystem tools do not know Yydra's semantics:

1. a Cargo-metadata checker for the allowed Product Workspace crate graph and role-specific dependency bans;
2. an OpenAPI-profile checker for Yydra's wire rules, in addition to generic OpenAPI validation.

Everything else can be composed from pinned tools. A passing baseline proves only the claims in the matrix; it does not promote Expo to the Golden Stack or establish native runtime behavior.

## Suggested fail-closed orchestration

`yydra check` should be check-only and phase-addressable for diagnosis, while its default contract runs all phases available on the current supported host:

1. **Preflight** — exact CLI/origin/tool versions, clean lock installation, required environment names present and secret values absent from diagnostics.
2. **Static core** — formatting, Rust/TypeScript compilation, Clippy/ESLint, Cargo architecture, OpenAPI/profile/generator/client drift, dependency policy.
3. **Database and service** — ephemeral PostgreSQL, migration fresh/upgrade checks, SQLx metadata when applicable, Rust/Jest tests, real Axum plus Schemathesis.
4. **H5** — production export and Playwright against the real service.
5. **Platform** — clean repeated CNG plus Android or iOS build on its supported runner; native runtime remains prototype evidence, not a default build claim.
6. **Evidence** — stable phase/result codes, tool versions, normalized reports, seeds, artifact digests, SBOMs, and raw logs. A report-upload failure must not turn a failed check into success.

Every required phase has three outcomes: `pass`, `fail`, or `infrastructure-error`; there is no implicit skip. A platform unavailable on the current host is reported as `not-run` and only accepted when another required CI job owns that phase. Local success therefore means "all locally applicable required phases passed," while merge success requires the complete CI profile set.

Exceptions should be narrow data, not warning suppression in command lines. Each entry names the stable rule ID, exact package/path/operation where applicable, rationale, owner, approval reference, and expiry or re-review trigger. Unknown rule IDs, expired exceptions, unmatched exceptions, tool warnings, nondeterministic generation, and missing evidence fail. Auto-fix, regeneration, dependency updates, `npm audit fix`, migration creation, and CNG repair stay outside `yydra check`.

## Decision boundaries retained

- The matrix supports the selected candidate; it does not demonstrate acceptable ordinary Product Domain edit cost or justify Golden Stack promotion.
- Architecture tooling can close import/dependency escape routes, but it cannot mechanically recognize "business logic in a handler." The vertical slice must include mutation tests that deliberately introduce each forbidden edge and demonstrate a useful diagnostic.
- H5 E2E, Android build, iOS build, Android runtime, and iOS runtime remain five distinct evidence claims. Jest, Expo Doctor, Expo Go, Web tests, or successful compilation cannot substitute for native runtime evidence.
- Dependency scans and SBOMs are inventories and known-policy checks, not legal opinions. Target-specific notices and every restrictive/custom/copyleft exception still need recorded human review.
- Reproducibility here means pinned inputs plus observable environment/evidence. Full bit-for-bit Android/iOS reproducibility is not established by these tools and should not be claimed in V0 without a separate experiment.
