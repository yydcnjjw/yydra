# Distribution 0.1.0 release procedure

Issue [#41](https://github.com/yydcnjjw/yydra/issues/41) owns release acceptance.
This procedure is not a declaration that the release has passed. Distribution
`0.0.3`, its tag, assets, catalog and evidence are immutable historical material.

## Delivery and input freeze

The maintainer selected GitHub-only delivery for this Goal. Do not run
`cargo publish` or request registry credentials. Dependencies may still be
downloaded from their locked registries. The supported installation artifact is
`yydra-cli-0.1.0.crate`, attached to `distribution-v0.1.0`, together with the
single-file checksum `yydra-cli-0.1.0.crate.sha256`. The crate's README documents
checksum verification, independent extraction and
`cargo install yydra-cli@0.1.0 --path ./yydra-cli-0.1.0 --locked`.
GitHub's automatic source archive and a source-checkout build are not substitutes.

Before creating the release package:

1. Check the live issue/dependency graph and authorizations. Verify the whole
   submitted commit range with `scripts/check-dco`. Preserve unrelated WIP.
2. Complete scoped tests, static checks and two-axis review; commit only #41
   changes. Record the exact source commit and use a clean checkout of that
   commit to package, without `--allow-dirty`. Keep heavy workloads serial.
3. Run `cargo package --package yydra-cli --locked` into an external package
   target directory. Record package SHA-256, normalized manifest and packaged
   `Cargo.lock` digest, `.cargo_vcs_info.json`, toolchains and file inventory.
   Verify the package is independently installable and contains no monorepo
   links, mutable templates, pre-generated native hosts or unrecorded inputs.
4. Upload the package and checksum to a draft GitHub Release targeting the
   exact candidate commit. Download those staged assets to a fresh directory,
   verify the checksum, extract and perform the documented locked installation
   into an isolated install root. Record the installed executable digest.

Repackaging can change archive/VCS identity even when source trees agree. Never
assign an earlier local package's digest to a new archive. If packaged inputs
change after freezing, discard no evidence: retain failed/old attempts separately
and validate a newly frozen candidate before publication.

## Packaged-consumer acceptance

Use only the installed executor from the downloaded release package for all
consumer commands. Keep Workspaces independent of the repository and of each
other. A local repository test suite is useful but cannot replace this seam.

- Create `clean-a` and `clean-b` with identical normalized inputs: `Clean Product`,
  `clean-product`, `Apache-2.0`. Compare their complete tracked path/kind/mode/byte
  inventories immediately after creation. Record the template, catalog, two
  Baseline Skills, Workspace Origin Records and Cargo/npm lock identities.
- In both clean Workspaces, run supported `doctor`, `setup`, `generate api` and
  `generate api --check`, followed by complete `yydra check --fixture clean`.
  That graph's `native.android-generation` node performs and compares two clean
  Android generations; its supported focused diagnostic form is `yydra check
  --node native.android-generation`, not a separate native-generation command.
  Both need complete passing evidence; comparing creation inventories
  and running `doctor` alone is insufficient. Record generation/lock integrity
  and keep evidence outside the Workspaces.
- Independently create `Reading Queue`, `reading-queue`, `Apache-2.0` and run the
  supported setup/generation path and complete `yydra check --fixture reading-queue`.
  Require real PostgreSQL/Axum behavior, Public API/Generated Client conformance,
  production H5 flows and registered semantics, deterministic native generation,
  and the account-free Android release build.
- Require the successful creation comparison, bound to the package/executor and
  recorded inventories, before continuing preparation, checks or aggregation.
- Run the same executor's aggregate command over `clean-a` and Reading Queue,
  then separately over `clean-b` and Reading Queue. Both aggregates must verify
  the complete retained evidence, not merely trust each manifest's pass fields.
  Preserve versioned
  manifests, JSON Lines, raw logs, checksums, locks, SBOMs, retained notices,
  provenance references and actual artifact inventories. Missing uploads or
  unverifiable retained files are not a passing release.

Required conformance nodes never retry into success. Infrastructure setup may
retry only under the existing recorded-attempt rules. Existing local #39 evidence
is prerequisite evidence, not proof that a newly packaged #41 executor passed.

## Publish and verify

Upload complete evidence archives and a release manifest binding source commit,
package, executor, input identities, commands, fixture/aggregate manifests and
every release asset checksum. Before publication, download the evidence archives
and verify the retained content with the same aggregate verifier. Draft staging
must not be described as a public release.

Publish only after all required acceptance passes and within the maintainer's
explicit authorization. Verify the published tag/commit and re-download the
public package, checksum, manifest and evidence; compare them with the frozen,
accepted bytes. Acceptance performed against staged assets must be identified as
such, with the post-publication equality check recorded. Do not silently replace
an accepted package, tag or evidence asset. Close #41 only after the public
artifact checks pass, then recompute and audit all Issue #26 children.

## Claims and exclusions

The claim is H5 end-to-end conformance and repeatable Android release builds on
the recorded host/toolchains, not bit-for-bit cross-host builds. Explicitly do
not claim macOS/iOS, Android runtime, physical devices, native accessibility,
Agent Eval, Baseline Skill effectiveness or complete WCAG conformance.

Dependency-license review, source/repository trust, upstream-source-to-binary
attestation and notice-completeness certification are not evaluated under the
maintainer's scope amendment. Preserve existing licenses/attribution and all
remaining version/lock, applicable-vulnerability, artifact and evidence-integrity
gates. Hashes establish byte identity, not those excluded reviews.
